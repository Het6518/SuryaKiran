Flows

The ML service (services/ml, Flask, port 5001) runs two unrelated models. The fault model answers "is this inverter failing, when, why and what will it cost" from hourly readings. The forecast model predicts power for the next minutes from a minute-level CSV. They share nothing: different inputs, different storage, different screens.

Fault model · inverter_pip_line.py

Input

Hourly reading

Required: inverter_id, timestamp, power_kw, pv1_power_kw, daily_kwh, inverter_temp_c, ac_voltage_v, dc_voltage_v, ac_current_a, dc_current_a, frequency_hz, alarm_code, price_per_kwh_inr. Optional: ambient_temp_c (defaults to inverter temp − 10) and op_state (defaults to −1, unknown).

Each /predict/single call appends the reading to that inverter's history (last 2,000 kept), saves it to disk, and re-scores the whole history.

Step 1

Feature engineering (28)

  • Power (10): power, PV1 power, DC→AC efficiency, delta, 12-h rolling mean/std, EWM(4), 48-h z-score, lag 1 h, lag 6 h
  • Temperature (8): temp, thermal rise over 12-h min, temp/power ratio, delta, rolling mean/std, EWM, lag 1 h
  • Electrical (8): AC/DC voltage & current, |freq − 50 Hz|, V·I DC power, DC/AC ratio, AC-voltage deviation from 48-h mean
  • Alarm (2): alarm code, count of >20 % power drops in last 6 h
Step 2

Labels

If op_state contains one of the configured fault codes, rows with that code are FAULT. Otherwise an Isolation Forest (100 trees, 5 % contamination) is fit on "healthy" rows (power > 0.1 kW, temp 5–80 °C) and whatever it flags becomes the FAULT label.

The API trains with FAULT_STATES = [2] (ml_service.py); the pipeline default is [3, 8] (Plant 3). All 22 saved models ended up on Isolation Forest proxy labels.

Prediction 1 · Is it faulty?

Weighted ensemble

wᵢ    = max(AUCᵢ − 0.5, 0) / Σ max(AUCⱼ − 0.5, 0)
score = Σ wᵢ · Pᵢ(fault) + 0.10 · [≥ 3 of 4 models say fault]
FAULT ≥ 0.30   WARNING ≥ 0.15   NORMAL otherwise

The Isolation Forest is trained but not part of the score. Backend maps to the UI: risk_score = round(score × 100); Critical if status FAULT or ≥ 80, High if ≥ 50.

Prediction 2 · When?

Time to fault

fit a line to the last 48 hourly scores
reliable if slope > 0 and R² ≥ 0.10
ETA_h = (0.30 − current) / slope

Otherwise "No fault trend". If the score is already above 0.30 the ETA is ~0 h.

Prediction 3 · Why?

Root cause

Global feature importance blended 50 % CatBoost, 25 % RF, 25 % XGBoost gain, summed into five categories: Power / Efficiency, Thermal, Grid / Electrical, DC / String, Composite. The largest is the "primary cause".

It describes the trained model, not the current reading, so it is the same answer every time for a given inverter.

Prediction 4 · Cost

15-day financial loss

project score 15 days on the 48-h slope
score → degradation:  <0.15: 0 %   0.15–0.30: 5–20 %
                      0.30–0.60: 20–60 %   ≥0.60: 60–100 %
loss ₹ = avg daily kWh (30 d) × degradation × ₹/kWh

Forecast model · forecast.py

Input

Minute-level CSV

timestamp, inverter_id, hour, minute, sin_time, cos_time, power_t-1, power_t-3, power_t-5, power_t-10, rolling_mean_5, rolling_std_5, pv_voltage, pv_current, optional target_power (falls back to power_t-1). Needs ≥ 15 rows per inverter.

Power

XGBoost + 2 baselines

XGBRegressor(300 trees, depth 5, lr 0.05) on the 12 features
recursive: each prediction becomes the next step's lag
exp  = last value repeated
lin  = 10-minute slope, extrapolated
w    = 1 / MAE on last 30 rows (one-step), normalised
power = w_xgb·xgb + w_exp·exp + w_lin·lin   (1,440 steps)
Risk

Risk score series

start = last value of 0.6·power-drop + 0.4·volatility
each minute: + (0.05 − r)·0.02  + power-change term
             + uniform(−0.005, 0.015) random noise
smooth with 5-minute rolling mean

Not a trained model. Contains unseeded random noise, so two uploads of the same CSV give different risk curves.

Storage

Where forecasts live

The ML service keeps forecasts in memory (FORECAST_STORE, lost on restart). The backend copies all 1,440 points into the ForecastPoint table and serves those when the ML service has nothing, which is why forecasts survive restarts.

Three different sources, which answer different questions. The research notebooks show what the approach can achieve with real labels. The saved models show what actually runs in the app. The forecast backtest re-trains the production forecast code on the CSVs already uploaded and scores it on the last day it never saw.

2 · Research notebook, Plant 1 (no faults in the test period)

False alarm rate on healthy data

The Plant 1 test set has zero fault rows, so recall, precision and AUC are undefined. The only thing measurable is how often each model raises an alarm when nothing is wrong (1 − specificity). Lower is better.

2,270,556 scored inverter-rows; LSTM was run on a 2,269-row subset and the ensemble on 54,756.

What this tells you

  • On Plant 3, with real labels, the supervised models are near-perfect; the unsupervised ones (Isolation Forest, LSTM autoencoder) are weak (F1 0.09 and 0.00).
  • On Plant 1 there were too few faults for supervised training, so models learned Isolation Forest proxy labels and still fire on 8–12 % of healthy readings.
  • The production app trains like Plant 1: proxy labels. Section 3 shows the result.
  • Plant 3 scores this high are worth one more check: alarm_code is an input feature and may move in lock-step with op_state. Re-running without it would show whether the model predicts faults or reads the alarm.

Against the few real labels that exist

Five inverters have a handful of op_state = 2 rows in their history (1–2 each). Scored with the production threshold (0.30). These rows overlap training data, so this is an upper bound.

Precision 0.002–0.003 means about 1 real fault per 300–600 alarms. With so few positives, treat recall and AUC as anecdotal.

Ensemble weights collapse to equal

Because every classifier copies the same proxy labels almost perfectly, their AUCs are all ≈ 0.995 and the AUC-based weights come out 0.24–0.26 each. The weighting scheme does nothing in production; the ensemble is a plain average.

Root cause share (mean of 14 distinct models)

Every one of the 22 inverters reports "Power / Efficiency Loss" as its primary cause.

Top 10 features (blended importance)

The two biggest drivers are the current power and the power one hour ago, which is consistent with models that learned "is power unusual" from the Isolation Forest.

Time-to-fault and loss outputs

  • ETA: 21 of 22 inverters return "No fault trend"; INV-01 returns "~0.0 hours" (already past the threshold).
  • 15-day loss: ₹0 to ₹106,042 for most inverters, but INV-267: ₹508,196,082, driven by an unrealistic daily_kwh in its history. The loss formula has no bounds.
  • Stored history spans Apr 2024 → Mar 2026: training data with live app readings appended on top, scored together.
